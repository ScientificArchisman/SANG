# Mouth rendering and lip-sync evaluation for SANG-M (LivePortrait renderer)

Evidence tags: [M] = measured number reported in a source (paper table / benchmark); [C] = claim by a source without a number or reproducible measurement; [I] = my inference. Date of research: 2026-09-30. Scope: rendering and evaluation side only (the motion model is covered elsewhere). Local SANG code was read for `sang/bench.py::lse`, `sang/syncnet.py`, `sang/motion.py::source_motion`.

## Q1. LivePortrait mouth rendering limits and lip modules; what LivePortrait-based audio systems do about the mouth

### Takeaway
LivePortrait's lip control is a 4-layer MLP trained only to reach a landmark lip-open ratio while leaving non-lip pixels unchanged. Nothing in its training targets teeth, tongue or mouth-interior fidelity, and users report generic "plate" teeth, teeth appearing on any jaw opening, and tongue ghosts, none of which have maintainer fixes [M code/paper; C issues]. Upstream applies `flag_normalize_lip` only in relative mode, and `expression-friendly` / `flag_lip_retargeting` do nothing useful for SANG's absolute driving. None of the six LivePortrait-based audio systems checked (Ditto, KDTalker, JoyVASA, Playmate, AVTR-1, Xemo-Talker) uses a mouth refiner or reports a mouth-quality metric; they rely on the LivePortrait decoder and report LSE from inconsistent pipelines.

### Cited Findings

#### 1a. LivePortrait paper (arXiv 2407.03168, v2 28 Feb 2025) — lip retargeting module
- [M] Architecture: "The lip retargeting module consists of a four-layer MLP with layer sizes of [65, 128, 128, 64, 63]" (input 65 = 21 keypoints x 3 + source lip-open scalar + driving lip-open scalar; output 63 = a 21x3 offset on all keypoints). Stitching MLP is [126, 128, 128, 64, 65]; eyes MLP [66, 256, 256, 128, 128, 64, 63]. — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [M] Formulation: Delta_lip = R_lip(x_s; c_s,lip, c_d,lip), then x'_d,lip = x_s + Delta_lip; loss L_lip = L1 of (I_p,lip - I_p,recon) outside the lip mask (keep non-lip pixels unchanged) + w_cond * |c^p_s,lip - c_d,lip| (the landmark-measured lip-open ratio of the output must match the requested scalar) + w_reg * |Delta_lip|. Trained in stage 2 (about 2 days) with the base model frozen; the driving lip scalar is sampled randomly during training. — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [C] Paper: "The lip retargeting module ... can also normalize the input by ensuring that the lips are in a closed state, which facilitates better animation driving." Fig. 9: "One can input a driving lip-open scalar c_d,lip between 0 and 0.8 ... and drive the lips from closed to fully open ... An out-of-training-distribution driving lip-open scalar can also achieve reasonable results ... Additionally, the tongue is generated when the lips are widely open." — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [M] Model scale: stage 1 trained on "69M video frames (92M before filtering) from about 18.9K identities and 60K static styled portraits", input crops 256x256, output 512x512, 8 A100 for about 10 days. — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [C] Stated limitations are only large-pose cross-reenactment and shoulder jitter; the paper does not discuss teeth, mouth-interior fidelity, or lip sync (the words "teeth" and "mouth" do not appear in the extracted text). — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)

#### 1b. LivePortrait code (repo now redirects to KlingAIResearch/LivePortrait; read 2026-09-30)
- [M] Lip-open ratio = `calc_lip_close_ratio(lmk) = ||lmk[90]-lmk[102]|| / ||lmk[48]-lmk[66]||` on the 203-point landmark set (inner-lip vertical gap over mouth width; larger = more open). `calc_combined_lip_ratio` returns the 1x2 tensor [c_s,lip, c_d,lip] fed to `retarget_lip(kp_source, ratio)`, which returns a 21x3 keypoint offset. — [retargeting_utils.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/utils/retargeting_utils.py); [live_portrait_wrapper.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_wrapper.py)
- [M] `flag_normalize_lip` (inference_config default True, CLI default False, "only take effect when flag_eye_retargeting and flag_lip_retargeting is False") with `lip_normalize_threshold: float = 0.03`: if c_s,lip >= 0.03, compute `lip_delta_before_animation = retarget_lip(x_s, [c_s,lip, 0])` and add it to every driven frame's keypoints (after stitching when stitching is on). Upstream only does this **when `flag_relative_motion` is True** (`if flag_normalize_lip and inf_cfg.flag_relative_motion and source_lmk is not None`). — [live_portrait_pipeline.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_pipeline.py); [inference_config.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/config/inference_config.py)
- [M] `flag_lip_retargeting` is annotated "not recommend to be True, WIP; whether to transfer the lip-open ratio of each driving frame to the source image". When on, x'_d = x_s + Delta_eyes + Delta_lip in relative mode (i.e. the driving expression is discarded; only the scalar ratios drive), or x_d + deltas in absolute mode, then stitching. — [argument_config.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/config/argument_config.py); [live_portrait_pipeline.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_pipeline.py)
- [M] `driving_option` "expression-friendly" (CLI default) vs "pose-friendly" (inference_config default): expression-friendly is only applied when relative motion, source image, driving video; it computes `motion_multiplier = sqrt(ConvexHull area(x_s)) / sqrt(ConvexHull area(x_d,0_new))` from the first driving frame and scales all subsequent keypoint displacements `(x_d,i_new - x_d,0_new) * motion_multiplier` added to x_s. Separately, `driving_multiplier` (default 1.0) applies `x_d,i_new = x_s + (x_d,i_new - x_s) * driving_multiplier` to every frame. — [live_portrait_pipeline.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_pipeline.py); [helper.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/utils/helper.py)
- [M] Lip keypoint indices used by `animation_region == "lip"`: [6, 12, 14, 17, 19, 20]; eyes [11, 13, 15, 16, 18]. In absolute mode the expression of keypoints [1,2,6,11-20] plus some coordinates of 3,4,5,8,9 are copied from the driving frame. For image drivers in relative mode, the driving expression is referenced to a stored `lip_array` (a canned closed-lip expression) rather than to driving frame 0. — [live_portrait_pipeline.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_pipeline.py)
- [M] Stitching: `stitching(x_s, x_d)` predicts a 21x3 expression offset plus tx,ty (65 outputs) and adds it to the driving keypoints; it is applied to all keypoints including the mouth ones, and it is trained to keep shoulders/borders aligned (paper Eq. with shoulder mask and L1 regulariser on Delta_st). — [live_portrait_wrapper.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_wrapper.py); [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [M] Licence: GitHub reports `NOASSERTION` for the repo licence (custom licence file; its terms and those of the bundled InsightFace detection models were not read here). Repo last pushed 2026-06-01, 289 open issues. — [GitHub API](https://api.github.com/repos/KlingAIResearch/LivePortrait)

### Inferences
- [I] In absolute mode, SANG's rendered mouth equals the generated lip keypoints warped from the photo's keypoints `x_s`. The renderer ceiling (mouth correlation 0.82-0.85) is the loss from LivePortrait's own extractor/decoder round-trip. The generated 0.65 correlation and 1.52x swing are a *motion* problem layered on top: no LivePortrait flag fixes them. `driving_multiplier` and `expression-friendly` are relative-mode scalings; an equivalent for SANG would be a per-coordinate affine rescale of the lip coordinates (keypoints 6, 12, 14, 17, 19, 20, and Ditto's jaw-open 'dimension 58' of the 63-d expression, which is keypoint 19 under either 0- or 1-based indexing, x or y coordinate depending on the convention) fitted on validation so the generated openness std matches GT. This is Ditto's "magnitude control" / AVTR-1's per-region CFG idea.
- [I] Stitching adds a learned 21x3 offset to *all* keypoints, including the lips, and is trained only for shoulder alignment with an L1 penalty. It could slightly damp or bias lip openness. SANG can measure this for free: re-extract lip ratio from renders with stitching on vs off on the same motion.
- [I] `flag_lip_retargeting` (ratio-only lip driving) would discard the DiT's lip shape (rounding, spreading) and keep only one openness scalar, so it is not a fix for sync. At most it could be a post-hoc *closure* tool for bilabials, e.g. forcing c_d,lip at about 0 on detected /p b m/ frames. SANG's issue is over-closure, though, so a floor rather than a push is needed.
- [I] Teeth problems (plate teeth, teeth on any opening) are decoder priors; they cannot be tuned away with flags. They can only be (a) avoided by choosing a source whose mouth interior is appropriate, or (b) overwritten by a mouth refiner.

### Gaps
- No quantitative study of LivePortrait mouth-interior quality (teeth sharpness, MUSIQ on the mouth, open-area ratio) under audio-driven motion was found; THEval gives LivePortrait a mouth-quality score of 0.9760, but in the video-driven setting.
- No measurement of stitching's effect on lip openness was found.
- The LivePortrait licence status (GitHub reports NOASSERTION) and the InsightFace model licence were not re-verified.
- The Ditto, KDTalker and Playmate papers do not say which SyncNet script, crop or fps they used; AVTR-1 prints no GT LSE row.


## Q2. Post-hoc mouth refiners after the renderer (sync/quality numbers, speed, licences)

### Takeaway
Post-hoc refiners are really mouth *re-generators*: LatentSync 1.6 (Apache-2.0, 18 GB, about 2-6 FPS), MuseTalk 1.5 (30 FPS at 256 px on V100, custom licence), and newer one-step systems (FlashLips 109 FPS, ComplexSync >70 FPS). They redraw the mouth from audio and ignore SANG's motion. They raise LSE-C, often above ground truth, and keep CSIM around 0.80-0.93 relative to their input. But their teeth are an "average mouth" (RGOR, 2026-09). LSE gains from SyncNet-supervised refiners are partly metric-gaming. Blind face restoration (GFPGAN/CodeFormer) does not improve sync and can hurt FID, texture and teeth.

## Q3. Choosing the source mouth state (closed vs slightly open, teeth visible)

### Takeaway
No source measures the effect of a closed vs open vs teeth-visible *source photo* on LivePortrait lip sync. The evidence is indirect: the LivePortrait paper says a closed-lip normalised input "facilitates better animation driving"; users report that mouth-state mismatches mix source and driving lips; and reference-based refiners do better when references show the person's teeth. The source mouth state is a cheap, untested knob that SANG should A/B directly.

### Cited Findings
- [C] LivePortrait: the lip retargeting module "can also normalize the input by ensuring that the lips are in a closed state, which facilitates better animation driving"; default `lip_normalize_threshold` 0.03 (paper Fig. 9 example sources have c_s,lip = 0.486 and 0.14 before normalisation). — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168); [inference_config.py](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/config/inference_config.py)
- [C] User reports (relative-mode v2i/v2v): lip sync improves when both the source and the first driving frame have "a neutral, closed mouth, with no teeth showing"; a source "smiling with showing teeth" only helps as a start point; talking source videos produce "a mixture of both the source and driving videos". — [issue 184](https://github.com/KlingAIResearch/LivePortrait/issues/184); [issue 114](https://github.com/KlingAIResearch/LivePortrait/issues/114); [issue 288](https://github.com/KlingAIResearch/LivePortrait/issues/288)
- [C] Mouth-interior failure modes tied to what the source contains: upper teeth "continue to be displayed without changing with the upper lip" (#176); teeth appear on any jaw opening (#565); a visible tongue in the source/driver persists "under the closed lips to some degree" even with lip-silent retargeting (#375). — [issue 176](https://github.com/KlingAIResearch/LivePortrait/issues/176); [issue 565](https://github.com/KlingAIResearch/LivePortrait/issues/565); [issue 375](https://github.com/KlingAIResearch/LivePortrait/issues/375)
- [M] LivePortrait's paper shows lips driven "from closed to fully open" with c_d,lip in [0, 0.8], and says "the tongue is generated when the lips are widely open", i.e. the decoder can hallucinate mouth interior absent from the source. — [LivePortrait arXiv 2407.03168](https://arxiv.org/abs/2407.03168)
- [C] RGOR (oral refinement) picks enrollment references "so that the teeth are often visible" because otherwise the rendered mouth is "an average mouth", and "the VAE of the latent generator compresses away the fine structure of the teeth and lips". — [RGOR arXiv 2609.38019](https://arxiv.org/abs/2609.38019)
- [M] SANG code (read locally, `sang/motion.py::source_motion`): SANG applies LivePortrait's lip normalisation (threshold 0.03, `retarget_lip(x_s, [c_s,lip, 0])`, converted to expression space by dividing by scale) to the **source motion vector used as the DiT reference**, not to the renderer's `x_s`. The warp still starts from the photo's true mouth state. Upstream LivePortrait instead adds the delta to every driven frame and only in relative mode. — [LivePortrait pipeline](https://raw.githubusercontent.com/KwaiVGI/LivePortrait/main/src/live_portrait_pipeline.py) (upstream behaviour); SANG repo `sang/motion.py` lines 362-379 (local)

### Inferences
- [I] Two competing failure modes for SANG's absolute-mode renderer:
  (1) A **closed-mouth photo** gives an appearance volume with no teeth/tongue. Every opening makes the decoder hallucinate a generic interior ("plate" teeth, blur), but closure for /p b m/ is easy because the warp returns toward the photo's own closed lips.
  (2) A **teeth-visible open photo** gives the person's real teeth when open. But closing requires warping lips over real teeth, which risks teeth or tongue leaking through closed lips (cf. #375) and possibly *stronger* closure deformations. That would be consistent with SANG's "closes harder at /p b m/" if the photos are open. Note that SANG normalises the reference motion but not `x_s`, so an open photo is still warped from open.
  A **slightly open, relaxed photo with upper-incisor edges barely visible** is the plausible compromise, but it is untested.
- [I] Proposed direct test (cheap, no training): pick 3-5 identities with three photos each (closed neutral; slightly open with incisors visible; open smile). Drive each with the same *real* motion (renderer ceiling) and the same generated motion. Measure (a) re-extracted lip ratio vs commanded (openness gain and closure depth at bilabials), (b) mouth-region MUSIQ, a texture ratio, and teeth artifacts, (c) LSE-C/D through the fixed pipeline, (d) CSIM. Also test "closed photo + renderer x_s normalised by retarget_lip" vs raw photo, since SANG normalises only the conditioning motion.

### Gaps
- No paper or benchmark isolates source-mouth-state effects on one-shot keypoint renderers; all evidence is user reports, LivePortrait's design claim, and refiner papers.
- Whether SANG's over-closure correlates with the source photo's lip ratio is unknown. This should be checked from existing demo logs (source c_s,lip vs closure depth).


## Q4. Reliable lip-sync evaluation (syncnet_python LSE-C/D, LatentSync SyncNet, AV offset, LMD, lip-reading WER, biases) + recommended plan

### Takeaway
SANG's nan is almost certainly a harness bug, not a SyncNet property. Since April 2026 joonson/syncnet_python logs results to stderr (SANG parses stdout) and refuses to reuse output directories. It also needs a system ffmpeg, face tracks longer than 100 frames (more than 4 s at 25 fps), and faces at least 100 px. LatentSync's `eval_sync_conf.py` is a clean Apache-2.0 Python-API alternative (same syncnet_v2 weights, `min_track=50`). LSE-C/D is pipeline-, codec-, crop- and shift-sensitive (±0.4-1.2 from codec alone; about 4 points spread for one method across papers). It is uncorrelated or negatively correlated with human preference (THEval ρ = -0.164). Generators can beat ground truth on it. So SANG must report it only against its own GT and renderer ceiling through one pipeline, alongside GT-relative openness, THEval-style audio-energy sync, silence stability, and a lip-reading metric (LipScore / AV-HuBERT).

### Cited Findings

#### 4b. LatentSync's evaluation code (what "Sync_conf" actually is)
- [M] LatentSync's "Syncconf" in its tables cites reference [9] = Chung & Zisserman, "Out of time" (ACCV-W 2016), i.e. the **original** SyncNet confidence (LSE-C), not StableSyncNet. Its `eval/eval_sync_conf.py` loads `checkpoints/auxiliary/syncnet_v2.model` (the same joonson weights), runs its own `SyncNetDetector(...)(video_path, min_track=50)`, evaluates every face-track crop, averages confidence and AV offset over tracks, prints "SyncNet confidence: x.xx", and raises "Face not detected in <video>" if there are no crops (rather than returning nan silently). The paper says "We found that Syncconf aligns closely with visual assessments." — [eval_sync_conf.py](https://raw.githubusercontent.com/bytedance/LatentSync/main/eval/eval_sync_conf.py); [LatentSync arXiv 2412.09262](https://arxiv.org/abs/2412.09262)
- [M] The data pipeline uses the official SyncNet to shift each training clip to zero AV offset and "remove videos with Syncconf below 3". — [LatentSync arXiv 2412.09262](https://arxiv.org/abs/2412.09262)
- [I] So "LatentSync Sync-conf" is not a different metric from LSE-C; it is LSE-C computed through a cleaner Python API with `min_track=50` (2 s at 25 fps) instead of 100. It is the easiest drop-in replacement for SANG's stdout-parsing wrapper (Apache-2.0). StableSyncNet (already ported in `sang/syncnet.py`) is a separate, stronger 16-frame discriminator; using it as an *evaluation* metric is non-standard and it is also the model SANG may train against, so it must not be the headline metric (train/eval leakage).

#### 4c. THEval (arXiv 2511.04520, Inria et al., v4) — metric validity
- [M] User study with 3,519 pairwise ratings over 17 methods: Spearman correlation with human preference LSE-C **-0.164** (p = 0.530, 95% CI [-0.613, 0.388]), LSE-D -0.269 (p = 0.297), FVD 0.289, FID 0.210, LMD-F 0.231, LMD-L 0.227; THEval final score 0.870 (p < 0.0001, CI [0.648, 0.967]); THEval's own Lip-Sync sub-metric 0.404 (p = 0.097), Lip Dynamics 0.527, Silent Lip Stability 0.484. (Fig. 1 prints slightly different values, LSE-C -0.148, LSE-D -0.255.) — [THEval arXiv 2511.04520](https://arxiv.org/abs/2511.04520)
- [C] Reason given for the negative LSE correlation: "Wav2Lip, trained with SyncNet as a discriminator, achieves top algorithmic scores by optimizing the metric directly, yet it was among the least selected methods in the user study." Listed limitations of LSE-C/D: poor human correlation, "ground truth was widely outperformed by generation results", and "instability to factors such as the cropped mouth region, image quality and brightness"; also sensitivity to head pose. — [THEval arXiv 2511.04520](https://arxiv.org/abs/2511.04520)
- [M] Encoding sensitivity (their SM B): switching the audio codec from mp4a (AAC) to mpga (MP3) changed LSE-D and LSE-C by 0.4 on average over HDTF, up to 1.2 for some clips; H.264 vs H.265 video gave similar shifts, with no visible difference to humans. — [THEval arXiv 2511.04520](https://arxiv.org/abs/2511.04520)
- [M] THEval's replacements: Mouth Quality = MUSIQ image-quality score on the landmark-localised mouth region (face uses TOPIQ); Lip-Sync = mean |O*_t - V*_t| over VAD speech frames between min-max-normalised mouth openness (upper-lower lip landmark gap / inter-ocular distance) and min-max-normalised RMS audio energy; Silent Lip Stability uses VAD (Silero) silent frames and lip-distance statistics; Lip Dynamics = variability of 40 lip landmarks; each metric is normalised relative to ground truth, so both too-little and exaggerated motion are penalised. Dataset: 5,011 clips, 6 languages (English 1,680, French 890, Chinese 733, Spanish 719, Japanese 645, Italian 344), mean 13 s. — [THEval arXiv 2511.04520](https://arxiv.org/abs/2511.04520)
- [M] LivePortrait (video-driven) THEval scores: Global Aesthetics 0.9464, Mouth Quality 0.9760, Face Quality 0.8784, Silent Lip Stability 0.9316, Lip-Sync 0.9980, Lip Dynamics 0.7548, Head Motion 0.9997, Eyebrow 0.9345, naturalness 0.9913; FLOAT and OmniAvatar are called out as exaggerating mouth movements (low Lip Dynamics / Silent Lip Stability). — [THEval arXiv 2511.04520](https://arxiv.org/abs/2511.04520)
- [I] THEval-style GT-relative lip dynamics is exactly the axis on which SANG fails (1.52x over-swing, over-closure at bilabials): LSE-C can go *up* when openness is exaggerated, so SANG needs a GT-relative openness metric beside LSE.

#### 4e. Beyond SyncNet: lip-reading-based and GT-relative metrics
- [M] **LipScore** (KeyFace, arXiv 2503.01715): "the cosine similarity between the generated and ground truth embeddings extracted from the final layer of a state-of-the-art lipreader", motivated by SyncNet's "low correlation with lip-sync quality and significant reliability issues even on ground truth data". HDTF LipScore: SadTalker 0.24, Hallo 0.27, V-Express 0.37, AniPortrait 0.14, EchoMimic 0.17, KeyFace 0.36. — [KeyFace arXiv 2503.01715](https://arxiv.org/abs/2503.01715)
- [M] KeySync (arXiv 2505.00497) uses LipScore instead of SyncNet ("shown to be more effective than the offset and confidence scores produced by the commonly used SyncNet model") plus **LipLeak** (feed silent audio with non-silent video; measure the fraction of frames where mouth aspect ratio exceeds an open threshold). Cross-sync LipScore / LipLeak: LatentSync 0.14 / 0.33, Diff2Lip 0.16 / 0.25, TalkLip 0.30 / 0.66, IP-LAP 0.17 / 0.28, KeySync 0.48 / 0.16. Caveat stated by the authors: DiffDub's "random lip movements" were "mistakenly interpret[ed]" by LipScore as better sync, which LipLeak exposed. — [KeySync arXiv 2505.00497](https://arxiv.org/abs/2505.00497)
- [C] TalkLip ("Seeing What You Said", CVPR 2023, arXiv 2303.17480) trains with a lip-reading expert and evaluates with lip-reading word error rate; it is the usual citation for WER-as-metric (not re-read here). — [arXiv 2303.17480](https://arxiv.org/abs/2303.17480)
- [I] For SANG, a lip-reading metric needs a VSR model (e.g. Auto-AVSR) and is language-specific (English-trained readers); LipScore needs GT video, which SANG has for held-out clips. Lip-reading WER on generated video is very noisy for short clips and non-English speech; use it only as a secondary, relative metric.

#### 4f. Other published criticisms of LSE / LMD
- [C] Yaman et al. (arXiv 2405.04327, CVPRW 2024) show LSE-C/D "are extremely sensitive to translation in the data, measuring poor lip synchronization performance when the face is shifted while preserving the same lip shape", and that SyncNet "demonstrates similar fluctuation on GT data". They propose AV-HuBERT-based metrics AVS_u (audio-visual, no GT), AVS_m (multimodal) and AVS_v (visual-only vs GT), computed as cosine similarity of AV-HuBERT lip-reading features. On LMD: it "is sensitive against shifting in the spatial domain", and "lips with different articulatory parameters (e.g., aperture and spreading) yield poor LMD score, although they are still synchronized". — [arXiv 2405.04327](https://arxiv.org/abs/2405.04327)
- [M] Ground-truth LSE is dataset-dependent and not an upper bound: HDTF GT LSE-C 7.73 (MuseTalk) / 8.243 (KDTalker); Talk9 GT 8.044 (Ditto); MEAD GT 8.04 (Xemo-Talker); NeRSemble GT 4.02 (RGOR), where LatentSync-1.6 scores 5.12 and HeyGen 5.37. — [MuseTalk](https://arxiv.org/abs/2410.10122); [KDTalker](https://arxiv.org/abs/2503.12963); [Ditto](https://arxiv.org/abs/2411.19509); [Xemo-Talker](https://arxiv.org/abs/2608.14700); [RGOR](https://arxiv.org/abs/2609.38019)

### Inferences
- [I] **Most likely causes of SANG's nan, in order**: (1) stdout parsing vs stderr logging after syncnet_python PR #78 (2026-04-17); (2) no face track, because clips are ≤4 s (`min_track` 100) or the face box after the 0.25x detection scale falls below the thresholds. A 512-px tight crop gives a face box of roughly 300-400 px, so size should be fine; a very tight crop where the face fills the frame can still fail S3FD at conf 0.9. (3) `ffmpeg` not on PATH on the compute node; (4) reused `--reference` directory; (5) scenedetect API mismatch on an old checkout. Each of these is swallowed by the wrapper's broad `except` or by its nan-on-parse-failure path. One run on `data/example.avi` (expect offset 3, min dist 5.353, conf 10.021) plus one real HDTF/test clip would separate harness bugs from detection failures.
- [I] SANG's own `StableSyncNet` port (`sang/syncnet.py`, LatentSync 16-frame model with a 1.3x zoom hack) is fine as a training loss/diagnostic. It should not be the reported metric, because it would be optimised against. Use joonson `syncnet_v2` LSE for comparability with papers, plus non-SyncNet metrics.
- [I] SyncNet's known bias toward exaggerated articulation means SANG's 1.52x openness swing may *not* show up as poor LSE-C; it may even raise it. The primary lip metric for SANG's actual problem should be GT-relative: the ratio of generated to GT openness std (target 1.0), bilabial closure depth relative to GT, and correlation with GT openness. These should be measured on re-extracted pixels (landmarks from the rendered video), not only in motion space.

#### Recommended rendering-side plan for SANG (ordered by cost; all [I])
1. **Fix measurement first (hours).** Replace the stdout parser: either import `SyncNetInstance` in-process and compute min-dist/conf from `dists_npy`, or adopt LatentSync's `eval/eval_sync_conf.py` + `SyncNetDetector` (Apache-2.0, same `syncnet_v2.model`, `min_track=50`, raises on no face). Also: put an `ffmpeg` on PATH (symlink `imageio_ffmpeg.get_ffmpeg_exe()`), pin the syncnet_python commit, use a unique `--reference` per clip or `--overwrite`, and evaluate ≥5 s clips. Log number of tracks, track length and per-track conf. Run the README sanity clip and one real test clip before any sweep.
2. **Three-row protocol, always**: GT video, GT motion re-rendered by LivePortrait (renderer ceiling), and SANG generated. Use the same crop (full 512 frame; do not pre-crop to the mouth), the same fps (25), audio as 16 kHz mono PCM, and the same codec (H.264 yuv420p crf 17 + AAC, or better, keep the audio as WAV and mux identically for all rows). Report LSE-C/D and the AV-offset histogram per row (a nonzero median offset in generated but not GT indicates an audio-feature alignment lag in SANG).
3. **Add GT-relative lip metrics on pixels** (re-extract landmarks from rendered frames with the same 203-pt LivePortrait landmarker or MediaPipe): openness std ratio, Pearson r with GT openness, mean closure depth on /p b m/ frames (from forced alignment, e.g. MFA/WhisperX phones) vs GT, and THEval's Lip-Sync (|minmax(openness) - minmax(RMS)| over VAD speech frames), Silent Lip Stability, and a LipLeak-style silence test (silent audio in, should give a closed mouth). Add mouth-region MUSIQ for teeth/blur.
4. **Lip-reading metric as secondary**: LipScore (cosine of lip-reader embeddings, generated vs GT) or AV-HuBERT AVS_u/AVS_v on English clips only; optional VSR WER on ≥5 s clips.
5. **Source-mouth-state A/B** (Q3 protocol) on 3-5 identities; also test normalising the renderer's `x_s` lips, not only the DiT reference motion.
6. **Renderer knobs to check (cheap)**: stitching on/off effect on re-extracted openness; a validation-fitted per-coordinate gain on the lip coordinates (target openness std ratio 1.0, floor on closure depth) applied before rendering. That is a motion-space post-process, not a refiner.
7. **Only then consider a refiner**: LatentSync 1.6 (offline, Apache-2.0, ≥18 GB) or MuseTalk 1.5 (real-time, check licence) on mouth only, with the source photo as the reference. Accept it only if it improves the GT-relative openness metrics and a blind A/B without CSIM loss > 0.01 or an FID increase. Treat LSE gains above the GT row as a red flag, not a win. Avoid full-frame GFPGAN/CodeFormer.

#### Evaluation protocol summary (for the report)
- Clips: ≥30 held-out clips, 5-15 s, identities unseen in training, 25 fps, English plus any target language, each with real video.
- Rows: GT / renderer-ceiling / SANG / (SANG + refiner).
- Metrics: LSE-C, LSE-D, AV offset (syncnet_v2, one fixed pipeline); openness std ratio, r(openness, GT), bilabial closure depth ratio, THEval Lip-Sync and Silent Lip Stability, LipLeak; LipScore or AVS_v; CSIM (ArcFace), FID/FVD, mouth MUSIQ; blind 2AFC A/B vs GT and vs previous SANG.
- Reporting: deltas vs GT row with bootstrap 95% CIs over clips. Never compare SANG's absolute LSE to other papers' tables.

### Gaps
- The exact failure in SANG's cluster run was not observed; the ranking of nan causes is inferred from code reading. SANG should capture stderr once to confirm.
- THEval's code and the Silent Lip Stability formula were not fully extracted (only partially visible in the PDF text).
- No study quantifies LSE sensitivity to crop tightness for LivePortrait-style 512 crops specifically; THEval and Yaman et al. report crop/shift/codec sensitivity in general.
- The LipScore lip-reader identity (reference [41] in KeyFace) and its licence were not checked; AV-HuBERT's licence is non-commercial research (not re-verified).
- The claim that SyncNet "rewards exaggeration" is supported indirectly (GT outperformed by SyncNet-trained models; THEval negative correlation; RGOR X-Dub open ratio 1.42). No controlled experiment scaling mouth amplitude against LSE-C was found; SANG could run one cheaply by scaling lip coordinates of GT motion by 0.8/1.0/1.2/1.5 and re-rendering.
